# v1.0.35 先运行再覆盖：配置继承、冷启动与发现边界

日期：2026-11-09。用户新反馈：先使用“35”玩一遍，识别出来后再覆盖新版，新版才能识别。本条针对这条新线索核对历史源码与持久化路径；不把“识别”自动等同于进程发现、Runtime 连接或主动按键成功。

**确认了可改变启动需求的旧配置继承机制，但尚未证明它就是用户现场原因。** v35 没有供新版复用的持久 PID／识别白名单，也不把成功的启动签名校验写成磁盘许可。此前已证明的共享采样冷启动环有明确配置前提；最新 pre.4 日志中已经连接并命令就绪的阶段不满足该前提。

## 版本与证据边界

本次“35”按真实正式 tag `v1.0.35` 核对：提交 `ff5a76ada06efdd764d9c3ef13cd452b4d69ef14`，`release_version.h` 为 `1.0.35.0`。它不是 1.0.43，也不是日志中的 1.0.43-pre.9。取得的历史文件及 Git blob 见 [source-fingerprints.json](evidence/pre1475-hotkey-input/v135/source-fingerprints.json)。

当前分析与下述配置夹具使用公开项目源码、受控配置存储和已有日志的脱敏字段，没有新增游戏 EXE、内存转储或真实 Windows 执行。没有新增原生 ABI、字段偏移或支持映像结论；历史 `Game::hWnd` 与 MRGA 信标入口事实仍分别以[后台发现记录](2026-11-04-background-renderer-discovery.md)及[v35 原始兼容记录](2026-10-22-platform5-135.md)为依据。

## 一、35 不会自动学习一个可供新版读取的进程名单

v35 的 `process_discovery.h`（blob `da4c12d6b36f262de8a99fe2b7cf39dbb4f4e54c`）按固定程序名、随机名称及磁盘映像指纹、窗口与窗口所属 PID 进行发现。该版没有 `process_target_selection.h`，`scan()` 没有 INI 写入或调用记忆目标接口。`process_image_identity.h` 的三秒匹配缓存只是进程内静态表，绑定 PID、创建时间与路径，不保存为文件。

当前版 [process_target_selection.h](../external_reader/source/process_target_selection.h) 才有 `Toolbox.ini/[GameProcess]` 的 `Keywords/ProgramCount/ProgramN`。这部分在显式修改关键词、添加程序、选择并记住进程时保存；自动扫描和成功附加不调用保存。`selectedPid/selectedCreation` 仅属于当前 Host 会话，没有持久化为下次启动的 PID。

因此，“35 玩一局生成进程识别缓存，覆盖后新版读取该缓存”不是这些源码支持的机制。当前名字表还保留了 v35 的固定名称并增加了别名，没有删掉 `gamemd-spawn.exe`。

## 二、旧目录会留下足以改变 Runtime 需求的功能配置

v35 `main.cpp` 缺省读取 `Hooks.Advanced=1`（兼容 `NativeOrders.EnableInputHooks=1`）及 `Hooks.AutoCS=1`。正常退出 `WM_DESTROY` 调用 `save()`，把当时的值写入 `Assist.ini`。该版还会保存缺省开启的 `Aircraft.ZWaypoints/WaypointMode`、`Production.ReserveNext` 等选项。

当前缺失开关的默认值为关闭；套件首次启动用 [initial_profiles.h](../shared/source/initial_profiles.h) 的 `CREATE_NEW` 建立 INI，已有文件返回成功而保留原内容。这项全关默认与已有文件保留政策从[1.0.37 设置记录](2026-10-24-stable-settings-137.md)已有明确依据。因此，新版放入新目录与覆盖到使用过的 35 目录，功能需求可能不同。

对 `Hooks.Advanced` 的最小执行验证见 [profile_demand.cpp](evidence/pre1475-hotkey-input/v135/profile_demand.cpp)、[原始运行日志](evidence/pre1475-hotkey-input/v135/profile-run.log)及[源码绑定报告](evidence/pre1475-hotkey-input/v135/profile-result.json)。夹具编译实际 v35／pre.4 的加载与保存语句，调用当前生产 `hookpolicy::resolve` 和 `runtimeFeatureDemand`；profile API 用内存键值存储替代，45 个实际编译头文件均绑定 SHA-256。**4 个场景、12 项检查通过。**

| 配置边界 | Advanced | OwnGround 键 | 相关 flags | `runtimeFeatureDemand` |
| --- | ---: | ---: | ---: | ---: |
| 当前全新默认 | 0 | 1606（Ctrl+Alt+F） | 0 | 1 |
| 仅保留基本手动动作，另取消 OwnGround | 0 | 0 | 0 | 0 |
| 从 35 的缺省配置继承 Advanced=1，OwnGround=0 | 1 | 0 | 0x2400 | 1 |
| 已明确 Advanced=0，运行 35 后保存，再由新版加载 | 0 | 0 | 0 | 0 |

`0x2400` 是 `AdvancedInput|NativeOrders`，可以独立形成 Runtime 需求。不过该表只验证特定功能需求函数，不能把它当成完整 INI 迁移、真实 Hook 或游戏运行结果；本轮修正后的总体 `needsBridge` 另有当前可读目标条件。

第四行尤其限定了因果：已有明确的 `Advanced=0` 时，35 读取并保存的仍是 0。不能声称“运行 35 一次必然把配置修好”。需要核对用户覆盖的目录、原 INI，以及是否同时保留了旧游戏进程。

35 的套件还默认启用并保存 `Modules.Cursor/Units/Assist`。当前套件兼容读取旧 Cursor/Units 状态，但仅 Cursor 订阅不会调用 Tactical 的 Assist 生产者，UnitMonitor 使用独立外读；两者不是 Assist 共享世界帧的替代生产者。单凭保留这两个模块的启用值不能打破 Assist 的冷启动环。相关边界为 `shared/source/host_game_input.h`、`game_runtime/source/runtime.cpp` 的 Tactical 分派及 Assist bridge 引入的 `world_frame_runtime.h` 唯一 `worldFrameServer`；不得把“加载了 Runtime DLL”扩写为“已经建立 Assist 连接”。

## 三、玩局生成的类型目录与兼容检查结果不承担识别职责

35 的 `rememberLiveTypes()` 在取得有效样本后更新 `Assist.ini/[TypeCatalogue]`，记录单位类型、ID、名称、费用等。当前消费者位于单位快捷键、科技清单和配额 UI；`discovery::scan()`、`resolveYrppWindow()`、`runtimeFeatureDemand()` 与 `needsBridge` 都不读取它。游戏布局校验中的类型数组来自游戏内存，不是把保存目录当成已经验证的游戏布局。

v35 `startupSignature()` 读取当前入口与精确的 MRGA 替换证据，`signatures()` 检查整表，没有写文件。当前 [startup_dependency_policy.h](../assist/source/startup_dependency_policy.h) 为编译期依赖分类；Runtime 的短期 `nativeDependencyCache` 也是内存状态。不存在“35 通过一次后把兼容结果持久保存，新版因此免检”的路径。两版的检查范围变化应与历史[依赖隔离记录](2026-11-04-platform-startup-dependency-isolation.md)分别讨论。

## 四、与已确认冷启动回归的关系及本轮修正

[版本源头研究](2026-11-09-hotkey-regression-origin.md)已把新增依赖环定位到 `944586abf9cd331d2aaf9fe24af744a593bd31d3`（1.0.44-pre.2）：共享世界消费者等 Runtime 出版首帧，`needsBridge` 却等外部显示样本或其他功能需求。关闭持续需求、取消默认 OwnGround、无既有桥和无排队命令时，基础主动键不能推动首次连接。**默认 OwnGround=Ctrl+Alt+F 是明确例外，不得把这个非默认反例称为开箱必现。**

旧配置若带有 Advanced 等需求，可绕过上述缺口；这解释了一种“覆盖旧目录比新目录更容易正常”的条件，但不能唯一解释当前反馈。v35 自身也早于这套共享世界传输；跨 Host 的共享帧受 owner、游戏身份和连接代次约束，不是一个可永久复用的磁盘缓存。

本轮在实际 tick 的 `needsBridge` 增加 `(enabled&&externalReader.canRead())`，其余需求项保留。`canRead()` 来自当前 `ProcessConnection.readable`，不依赖已发布世界样本、类型目录或上次运行。仍保持注册检查→`sampleExternal`→需求判断→`ensureBridge` 的顺序：首轮消费可失败，随后建立生产者，下一轮再消费并注册基础动作。前面的无游戏窗口／只读显示返回，以及 `ensureBridge` 的启用、原生 HWND/PID/TID、ABI 与重试退避保护均保留，没有放宽命令、聊天、前台或跨 PID 保护。

[hotkey_cold_start.py](../assist/tests/hotkey_cold_start.py) 编译完整生产采样、合并、命令身份和注册函数；固定的 pre.4 三句调用点作为负对照。当前执行 **11 场景、77 检查通过**，旧调用点在 `manual_only/manual_restart/delayed_connection` 三个场景共 18 项断言失败。默认 OwnGround、继承 Advanced、自动维修、预先连接、不可读目标、仅查询权限、禁用、连接延迟与世界出版延迟均有区分。`manual_restart` 是清空 Host 状态后再次冷起，不代表执行了 Windows DLL 卸载或真实游戏重启。

本轮最终 `final-checks/execution-summary.json` 记录 34/34 项当前源码执行通过，摘要 SHA-256 为 `7efdc91c266564bdc63f8a03f6f5051513de9f43b56d2199135ed3b6e7249ece`；其中冷启动结构化报告 SHA-256 为 `e052fb6ef8805919ce499e486c8f29396928d0d9f3f5af775b82da2fae777757`。这属于受控 Linux/生产片段检查，不是 Windows 实机、游戏、性能或联机验收；最终二进制与源码绑定以发布 manifest 为准。

## 五、最新 pre.4 日志的反证与下一次判别

[脱敏发现摘录](evidence/pre1475-hotkey-input/v135/pre4-discovery-excerpt.json)只保存行号、时间、别名和白名单状态字段，原始日志及用户路径没有进入仓库：

- 2225 行，16:18:34.722：`knownNames=1 remembered=0 explicitSelection=0 descriptions=0`。
- 2226 行，同毫秒：读取附加成功。
- 2232 行，16:18:34.885：安装 Hook。
- 2237 行，16:18:34.912：`stage=connected`。

这次实际成功连接使用固定名称，未命中记忆名单。发现后约 163 ms 安装 Hook、约 190 ms 已连接。此前 `candidates=0` 阶段没有足够操作时序，不能仅凭日志判断那时游戏是否已经存在。

随后已有 commandStatus=1、fresh=1、非零功能需求和完整显示样本，却未观察到主动输入，详见[pre.4 实机失败记录](2026-11-09-hotkey-pre4-live-failure.md)。**本轮冷启动修正不能被宣布为这段已连接现场的唯一根因或已修复证明。**

最有区分力的后续对照是：同一新版二进制、游戏完全重启，只交换失败配置与 35 生成的配置，检验 INI 继承；再保持配置不变，比较游戏重新启动与保留旧游戏进程，检验运行时寿命。若失败时已有 `read-attached` 与健康命令通道，应继续检查输入门控；只有已确认目标游戏存在而发现仍是 `candidates=0`，才属于真正的发现链问题。
