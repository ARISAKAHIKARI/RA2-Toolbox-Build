# 关闭硬件断点、全部工具箱计算时的游戏侧开销

日期：2026-11-08。基线为 1.0.45：公开源码 `2e4c1443c61312744a1806a29e546ef4fa9a5b56`；本地等价树提交 `88812eda0d23d065d61d6f742315b7d0581fd1a8`，二者完整树均为 `bbf1f646ef15632af6edc88c833fe01e8534ef95`。目标版本为 1.0.46-pre.1。

## 结论与范围

用户报告硬件断点全部关闭、计算位置全部选工具箱时，游戏本身仍变卡。源码证实该模式仍在游戏线程捕获原始世界、整理战术输入、发布给 Host，并在最后执行原生查询与指令。只观察工具箱中的 Planner 计算时间不能反映这些成本。

这轮优化游戏线程与 Host 数据交接路径中的确定冗余，不降低采样频率，不添加游戏地址、补丁点、原生 ABI、读取权限或新的实时读取回退。此前每个成功重叠字节只采集一次的设计、分发协议、后置世界身份核验及手动操作/提交新鲜度检查继续保留。

没有进行原生 Windows、真实游戏、物理 GPU 或多人联机验证；下列受控数据不构成游戏 FPS 提升比例，也不能证明所有实机卡顿已经解决。

## 发现及修正

### 1. 无硬件功能时仍执行私有 INT3 槽位诊断

`maintainTechParameters()` 位于普通战术频率门控之前。旧代码即使所有硬件功能都关闭、调试页不可见，仍每 500 ms 调用 `Service::inspect()`，通过游戏所属线程上的私有 INT3 读取调试寄存器；这条路径会注册/移除 VEH、复制/关闭线程句柄。它不是硬件执行断点的命中。

现在仅在明确打开调试诊断时进行这类空闲检查。功能启用的真实寄存器准入、活动时的审计、停止/故障/待恢复处理均维持原行为。普通状态显示“实际占用未测定，启用时复核”，不会将未知状态显示为零占用。

### 2. 小型规划也复制完整固定容量 World

`publishPlanningWorld()` 的 `planningWorld=w` 无条件复制 6,336,544 字节；小型规划与大世界承担同样的保留副本成本。此外，在无任务/同帧重复早退之前，旧代码还复制 81,920 字节的武器缓存用于回滚。

`copyActiveWorld()` 先校验各计数及精炼厂等待列表，再只复制有效数组前缀和全部头字段。保留 World 的地址稳定，非活动槽位不会成为有效数据。武器缓存快照移到无任务/同帧早退之后；正常失败、手动代次与提交阶段的检查保留。

### 3. Host 每次接收规划都分配并初始化 6 MB World

`servicePlanner()` 每次新修订都 `make_shared<World>()`。改为最多三个延迟分配的槽位，只复用 `use_count()==1`、仅被池自身持有的 World。工作线程 `Task` 会为其内部索引保留上一份 World，这种持有仍然阻止复用。

如果三个槽位均被持有，本次收集延后，不改变世界修订号、不丢弃待处理回执，也不覆盖运行中的输入。原有计算批次与世界 seqlock、帧/局身份、过期和未来帧检查继续在相同位置执行。

### 4. 每帧采样创建数千个集合节点，读取逐 4 KB 发起

`CaptureGraph` 原有临时 `unordered_set` 每帧为对象、类型与辅助对象分配节点；列表、队列和时间链去重也反复分配。Runtime 现在持有复用的 `CaptureScratch`，集合使用有代次的扁平桶，工作队列保留容量；每帧清除的是成员资格，不保留上一帧的观测结果。

发布实现保留原有逐页与局部范围读取：采样页面、有效内容和成功/失败语义保持一致，仍使用安全的 `ReadProcessMemory`，未改为无保护的直接解引用。请求列表在 Runtime 内保留容量，每帧重建当前需求。

还比较过最多 16 个相邻页合并读取的方案。它确实减少 reader 调用次数，但需要先读取连续 scratch，再复制到固定 Page 格式，部分纯 CPU 场景明显变慢。以五个相同输入场景比较原有 Runtime 内存函数与新函数，合并方案即使配合新内存函数仍在三个场景回退；不能仅凭尚未测量的 Windows RPM 调用成本断言净收益。因此本版移除该方案，采用复用工作区和原读取方式，并在单独的实验记录中保留反证。该实验的读取次数改善不能计入本版收益。

### 5. Runtime 的全局内存原语是低效逐 DWORD 循环

Runtime 在 `-fno-builtin` 配置下提供全局 `memcpy` 和 `memset`，旧实现使用 volatile DWORD 循环。这使采样页初始化、共享载荷及规划数据都使用同一低效路径。

新的共享实现对小块采用不要求对齐的标量复制，大块采用带明确方向标志及寄存器/内存约束的 x86 字符串指令。检查针对实际 Windows x86/x64 目标生成代码，防止编译器把实现再次折叠为递归 CRT 调用或加入额外 SIMD 依赖。

## 未在本轮修改的路径

- `setFrameSampling` 与 Host 轮询频率未改变。`externalDisplay` 是握手标记，并不能直接当成可见窗口的工作需求；只删去“非全游戏计算”条件不足以证明实际工作减少。
- 防偷家候选预扫描仍保留；未经证明的跨帧缓存不能替代配置代次及最终准入检查。
- 原始页的有效覆盖、跨进程发布与 Host 导入仍有必要成本，地图/视图需求增大时不会消失。
- 现有 `scanMicros` 的计时起点晚于部分维护与早退路径，不能用它单独证明整条 Runtime 消息路径的耗时。调试页显式打开时保留槽位诊断，因此对比时应维持一致状态。

## 已执行的对比结果

固定基线与最终生产函数的有效输出摘要保持一致。下面的数量为对应夹具的实际结果，并非整局游戏的总工作量：

| 工作 | 原实现 | 发布选定实现 |
| --- | ---: | ---: |
| 两个对象、一个精炼厂的保留规划副本 | 6,336,544 字节 memcpy | 2,152 字节 memcpy，另写 32 字节头字段 |
| 1,000 次空闲或同帧重复检查的回滚复制 | 81,920,000 字节 | 0 |
| 2,500 次稳定 Host 接收的大 World 分配 | 2,500 次 | 池预热后 0 次 |
| 8,192 对象采样的稳定堆分配及释放 | 每帧分别 8,588 次 | 分别 0 次 |
| 同一采样输入的页数、读取次数、读取字节与有效输出 | 固定基线 | 全部相同，包括稀疏失败场景 |
| 10 秒虚拟时序、硬件全关、诊断隐藏的私有 INT3 | 20 次 | 0 次 |

Host 池最多保留三个 World，约 18.13 MiB，按需分配。首次增长或较大世界仍可能分配，不能将预热后的“0”理解为程序终身不再分配。

定向检查包含：16 个采样新旧比较场景 / 6,040 检查，74,634 个便携采样检查及 75,357 个模拟平台检查，16 个空闲诊断场景 / 32,602 检查，完整战术采样夹具，规划副本与真实 Planner/Task 所有权检查，41,156 项内存语义与边界检查，以及 Windows x86/x64 代码生成核验。模拟的 Win32 边界不是实际 Windows 执行。

规划发布的最终受控中位数为 500 次 280.160 ms → 3.348 ms；Host 接收夹具为 500 次 315.615 ms → 0.131 ms。内存函数、采样与规划的不同夹具不可相加或换算成 FPS。

采样计时出现明显运行间波动：选择实验曾得到五个场景均较快，最终单次配对重放中 8,192 对象场景则为基线 8,630 µs、选定实现 9,467 µs。并发编译影响的一次运行和配对重放均保留；没有挑选最有利的一轮，也不主张固定的总体加速比例。确定性证据是删除了稳态分配/释放，并保持读集与有效输出；实际游戏收益仍需在同一存档、同一设置下比较。

## 复现与证据

完整定向记录见 [验证输入和源码绑定](evidence/toolbox-compute-146/validation-inputs.json)。同目录保存原始结果、调度波动记录，以及标为 `NOT-SHIPPED` 的被拒绝批量实验。`benchmark-harness` 保留实际执行的原始脚本及源文件；其中绝对路径属于当时执行记录，复现时应指向自己的 checkout 和输出目录。

定向检查、原始计数、源码摘要、构建与包摘要分别保存；本轮生产改动与测试输入的最终摘要在发布前核对，Windows 目标编译及 PE/协议结果由冻结构建清单记录。历史其他功能检查不计作本轮重跑。

实机对比应使用同一存档、视角、单位规模与功能开关，硬件断点关闭、计算位置全部选工具箱。替换更新时完整退出游戏与工具箱，避免仍驻留在游戏内的旧 Runtime 使对比失真。
