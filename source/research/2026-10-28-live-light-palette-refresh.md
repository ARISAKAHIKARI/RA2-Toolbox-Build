# 素材高刷：现场光照与运行时色表失效

继续 `experiment/render-upgrade-v139pre6-20261028`，基线 `ae5906319293e97bb387585973e033c046db26fb`。本轮修正 RenderMaterial.1 的现场光照缓存缺口，复用既有光照／色表读取布局，没有新增游戏代码段修改、调用、网络事件或逆向地址结论。

## 修正

1. 主视口撤销整幅不透明画面的 `heldFrame` 快捷复用。即使逻辑帧号、位置、姿态、相机和资源版本都不变，每次呈现仍执行光照合成与特效读取。模型、SHP 索引／解码结果继续保留。VXL 不再保留跨呈现帧的已着色姿态：插值的是位置和身体／炮塔角度，然后按当前 VPL、色表和现场光照重新栅格化／着色；不会在两张 VXL 成品图之间做混合。
2. 显式建立每次呈现的只读页缓存周期。已有 `ProcessReader::open` 对同一存活进程本来就会调用 `begin`；此处将这一要求写在呈现入口，不把它误报为旧版跨呈现页缓存错误。
3. 色表按完整内容刷新：每次取得两份一致的 256 色输出，并核对 live/file 来源。转换器和色表地址不变、原地址的 RGB 或 RGB565 字节改变，也会失效对应彩色姿态。读不到、读到不一致内容，或曾经的 live 来源只能退到文件色盘时，不替换为未经确认的颜色。
4. 颜色改变只清除受影响素材的彩色姿态及旧姿态回退引用，不重新捕获模型／SHP。中间动画的两个端点都使用当前确认的色表。地形色表和覆盖物色表同样参与内容检查。
5. 动画和弹体的缓存键包含对象地址、ID。两个同类型、同所属方动画可以使用不同的对象转换器，不能共享已经着色的图片。
6. 每次呈现重新取得当前原生 VPL 内容；读取失败或撕裂时不继续使用旧 VPL 或替代的 Lambert 光照。VPL 变化不清掉已捕获的模型，而只影响本次着色。主视口、小地图实景渲染器与副相机都采用实时 VXL 路径；新素材发现仍有工作预算，但已捕获的当前 VXL 不被 8/16 项发现预算冻结在旧图片。副相机也采用逐对象色表失效；来源恢复后重画。
7. 场景渲染失败时，worker 返回明确的空图像结果，以替换 Latest 中的旧场景。不能仅返回空指针，因为 Latest 的语义是保留上次结果，这会让旧光照画面继续覆盖原游戏。

地形背景还需验证每格已求值的亮度、色调、桥与覆盖物状态，而不能只比较全局环境光。当前视口依赖优先验证；发生变化时，在新背景准备好之前撤回外部场景，显示原游戏画面。小地图完整地图扫描仍按有界批次处理。

## 验证

- `live_palette_cache.cpp`：相同地址的内容改变、未改变复用、撕裂／失败读取、来源降级拒绝，以及地形 RGB 的两次一致读取。
- `game_assets_host_test.py`：实际生产捕获／解码路径的 LightConvert、普通 RGB565、覆盖物和 ColorScheme 原地修改，来源不可读与恢复；模型和 SHP 字节保持原缓存。
- `live_scene_lighting.cpp`：同一个 Frame／逻辑帧／姿态，单独改变环境光、局部光、转换器色调与调色盘；检查最终像素、地形缓存、对象独立性和几何捕获次数。
- `watch_live_palette.cpp`：副相机同帧颜色刷新、局部失效、对象隔离、不可读与恢复。
- `validate_material_refresh.py`：禁止重新引入整帧复用捷径，要求失败结果撤回旧图片；结合既有 Runtime 源码哈希契约验证呈现改动没有修改旧命令／补丁实现。

这些是受控内存与像素回归及构建验证，不是实际游戏或双机联机证明。完整原版特效、实战帧率和端到端延迟仍需实机测试。当前 VXL 方向光／默认投影常量沿用已验证的原版 YR1.001 数据；特殊模组动态方向光矩阵尚未支持。模型仍含捕获时的静态 HVA 变换，没有新增逐帧 HVA 动画采样，不能把它称为所有原生状态的完整复刻。移除整帧快捷复用会增加静止画面的合成开销，500 Hz 仍只是可配置的目标。

更新需先退出游戏和工具箱，再成套替换 EXE/DLL，保留原 INI。渲染升级和素材高刷入口沿用 RenderMaterial.1。
