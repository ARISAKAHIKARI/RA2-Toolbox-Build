# 1.0.47-pre.2：操作确认、目录和渲染缓存的失败恢复

本轮修复工具箱自身的状态机、目录重建和图像缓存事务。没有新增游戏可执行样本、函数地址、字段偏移或 ABI 结论；游戏 EXE SHA-256 不适用。已沿用现有研究索引和文档中的接口，不包含用户游戏文件或原始转储。

四组定向测试使用实际生产代码，并对同一套测试运行冻结 pre.1 源码的负向对照。原始日志、执行命令、退出码和 SHA256 绑定见 [本轮证据目录](evidence/pre147-functional-recovery/index.json)。本轮 Windows 目标交叉编译、PE 检查、完整源码同步及安装包回读另由冻结交付回执记录；不能将 Linux 夹具解释为 Windows、WebView2、游戏、物理 GPU 或联机执行。

## 控制台：状态快照不能替代操作回执

### 已确认的问题

`ConsoleStore.receive(state)` 原先只要看到快照值等于 pending 的目标值，就会提前移除尚未收到 ACK 的操作。例如迅速把开关“开→关”，较早的快照仍然显示原来的“关”，它与第二次操作的目标相同，却不能证明第二次操作已执行。pending 被清掉后，对应序号的拒绝 ACK 无法匹配，失败提示随之丢失。

这不是凭空假设的消息顺序：现有原生发布器每轮最多发送 32 条 ACK，然后发送状态快照。因此队列中的某个操作可以先观察到快照，之后才收到自身回执。

### 修复与验证

快照只有在该操作已经收到匹配成功 ACK 后才能确认操作，继续遵守既有 `seq`、`generation` 和 `requiredRevision` 规则。快照先到、成功 ACK 后到时，ACK 可使用已经观察到的 revision 完成确认，不需要人为等待另一份状态。旧序号、旧 generation 和较晚本地草稿的隔离规则保留。

专项在 Node VM 中直接执行生产 `app.js` 的 `ConsoleStore`，覆盖五种设置值、两种 ACK/state 顺序、归一化 revision、快速回转、迟到拒绝及后续本地编辑。没有把 VM 当作浏览器或 WebView2 验收。

## 控制台：仅聚焦不应触发放弃修改提示

获得焦点时创建 draft 是为了防止动态状态覆盖正在编辑的文本；原关闭检查直接计算 `drafts.size`，因此只点进输入框、没有改变内容，也被认作未提交修改。

关闭检查现在将草稿与当前有效页面的已确认控件值比较，只计算真实差异。尚未 ACK 的操作、来源未知的草稿和已退役 generation 的页面仍按未提交处理。检查只读，不清草稿、不隐式提交，也不改变原生关闭策略。每个涉及页面只建立一次控件索引，避免为每份草稿重复扫描整个页面。

验证包括未改文本、数字、可编辑选项和滑块、编辑后撤回、真实改动、过期页面、未 ACK 操作及 10,000 计数上限。两项控制台修复合计 **24 项专项通过**；冻结 pre.1 对照有 **18 项失败**。已有 ConsoleStore **35 项回归通过**。已有大状态测试增加实际需要的成功 ACK，仍检查其他草稿不受影响；没有把旧的不正确自动确认行为固化成新要求。

## 单位统计：不完整类型目录必须能在下一份样本恢复

`Sampler::sample` 先采集目录指纹，再另外读取类型表。原 `types()` 遇到 cameo、ID 或构造条件短读时会跳过类型或使用默认值，数组读取失败也可表现为空类别。只要其他类型仍然存在，已经成功取得的目录指纹就保持就绪。后续健康样本的指纹没有变化，残缺目录便可能一直不重建。

现在数组头、成员和目录必需字段必须完整读取。失败时撤销整个派生目录，清空当前统计和类型索引，并撤销指纹就绪状态，让下一份健康样本重新构建。新增内部诊断 `UnreadableTypeCatalogue`，提示“单位类型目录读取不完整，等待下一次完整采样”；枚举追加在末尾，已有数值不变。合法空数组、已知缺少图标的过滤以及原有容量上限继续保留。

测试刻意让指纹读取先成功，再在后续建表阶段制造一次短读，覆盖 cameo、ID、级别、Owner、Insignificant、Spawned、数组地址、容量、数量和成员十类故障，分别检查冷建表和已有目录重建。专项 **21 场景、93 项检查通过，20/20 目录恢复**；pre.1 同样本为 **60 项失败、0/20 恢复**。已知空数组和 `none` 图标控制通过。

附加验证包括既有 **26 项对局切换回归**、异步采样及阻塞期间失效检查，以及新专项 ASan+UBSan。此次 sanitizer 显式关闭 LeakSanitizer，不宣称做了泄漏检测。重建不引入另一份大型候选 Snapshot，也没有改变采样时点或所有权统计规则。

## 矿车让行：只有进入最终批次才消耗重试预算

原规划器生成 OreYield 候选时就增加尝试次数并记录发送帧。随后矿车与战斗候选交错合并到最多 32 项的最终批次，一部分候选被截掉，却已经消耗重试预算。这些未返回的候选不可能收到 Accepted、Rejected 或 Expired 回执，持续竞争时可能从未交付就耗尽重试额度。

现在在候选真正进入最终返回批次时才更新该矿厂让行轮次的计数和时间，并匹配矿厂、被让行单位及 token。已返回订单仍遵守原重试间隔、次数上限和三种回执策略；交错顺序和批次容量保留。

独立复核还发现：原先更新 `sent` 的副作用会抑制重复 Actor 输入形成的同帧候选，直接延后更新会失去这层保护。初稿在同一远端矿车重复一次、提供两个等待格的合法输入中，两帧发送四次，超过原三次上限。最终修复在选择等待格之前，对当前最多 32 项候选按矿厂和 OreYield 类型去重，保留第一个候选。旧版和最终版均在帧 500、530、560 各发一次，保持首个等待格，累计三次；未扩大所有订单或任务列表的去重范围。反例和独立复核日志一并保留。

| 受控输入 | pre.1 | 修复后 |
| --- | ---: | ---: |
| 20 个让行候选 + 32 个战斗候选，首次返回让行 | 16 | 16 |
| 同次被计为让行尝试 | 20 | 16 |
| 下一帧返回上次遗漏的让行 | 0 | 4 |
| 32 + 32 候选，下一帧返回上次遗漏项 | 0 | 16 |

专项直接执行生产 Planner/Task，最终 **136 项检查通过**，覆盖混合容量压力、纯矿车批次、重复 Actor、三类回执上限和 generation 重置。未补候选去重的初稿在增强专项中出现 23 项失败，最终均已闭合。已有 ore_priority **28 场景**、planner_tasks **240 帧对照及阻塞 worker 失效**、external_planner 回归在最终头上重新通过，新专项 UBSan 通过。这些是受控世界快照中的规划结果，不代表 Windows 原生命令投递或游戏已经执行了命令。

最终测试还与冻结 pre.1 原头做了同字节对照，编译成功、运行退出 1，出现 **12 项失败**。旧版缺少返回订单，逐返回项检查少执行 24 次，因此基线实际计数为 112，不能将这个差值解释成测试案例变化；测试 SHA256 与当前 136 项通过的版本相同。

## 保存建筑与动画：缺读不能永久缓存为有效图像

`Layers::sprite()` 原先在保存建筑或动画的部分元数据读取失败时采用默认值，仍将图像写入持久缓存。恢复健康读取后，同一个 `Layers` 会继续命中错误的遮挡、裁剪或深度图像。仅拒绝当前场景不足以解决已经写入缓存的错误结果。

影响图像的元数据读取现在参与完整性判断，失败不能提交当前调色板或持久图像。非零但不能解码的 BUILDNGZ 也不能当作已知无深度遮罩；已读 null、宽度至少 8 和 `noZShape` 的合法路径保持原行为。正常缓存命中仍复用原有图像所有权。

测试通过生产 `Context → SHP 解码 → Layers::frozen → Surface / SceneRenderer` 路径，覆盖九类缺读、畸形非零遮罩、动画调色板选择和 Flat 标志失败。恢复使用同一个缓存，不依赖清缓存或人为更换资源身份。

| 验证 | 冻结 pre.1 | 修复后 |
| --- | ---: | ---: |
| 专项检查 | 109 项中 45 项失败 | 109 项全部通过 |
| 9 个 Layers 恢复与健康参考累计像素差 | 4,032 | 0 |
| 12 个实际 SceneRenderer 恢复累计像素差 | 7,652 | 0 |
| 健康输入摘要 | `b87ea9343f6207a3` | 同值 |

这些是 CPU 渲染代码的受控像素对照，不是游戏截图或物理 GPU 验证。
