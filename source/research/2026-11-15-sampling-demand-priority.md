# 补采需求及时提交：避免 2ms 合并窗口等待下一轮消费者

用户目标：继续优化采样可靠性、及时性，同时控制游戏进程阻塞。基线为已发布 pre.9 `b64b9007e2bc1cd4cab1c54d7870e62fa680b26d`。本次仅修改 Host 读取会话到共享需求队列的路径；无新增游戏地址/字段、Hook 或 ABI，非游戏逆向发现。

## 已复现的等待

`Client::publishRequests` 对需求集合更新设置 2ms 间隔，但没有独立的到期刷新任务。第二个消费者在上一次提交后1ms内缺页，`ProcessReader::endWorldFrame` 原来没有传递本次完整性，补采需求因此仍走常规合并；若消费者下一次在16ms/50ms后运行，请求就多等一轮，实际不只是2ms。

## 改动

- ProcessReader 把 `!worldComplete_` 传给共享需求队列，派生显示帧继续走独立 visual 请求路径。
- 本次未读全且需求集合发生变化时，立即提交合并后的集合；相同集合只续租，不增加 revision 或复制整张页表。
- 成功读取保留2ms合并；过期清理继续检查最早有效期，紧急需求可及时回收已过期容量，不驱逐有效需求。
- Runtime 采样频率、每逻辑帧复用、失败退避、封口快照、时间戳和跨帧/跨局核验保持原合同。这里只让需求更早可见，不声称保证立即采到，也不把补页拼入已封口控制样本。

## 验证

`world_frame_retention.py --negative-priority` 执行实际 Client/Server/ProcessReader 和共享内存代码，Win32 I/O 为原有受控替身：在第一次需求提交后1ms制造必需字段缺页，当前需求立即对 Server 可见；旧版实际 `endWorldFrame` 函数的失败对照可复现等待。检查重复失败不重复提交、成功需求仍合并、无新增实时读和旧样本不刷新时间戳，并回归依赖续租、完整发布保留、失败重试、暂停需求和未完成需求。

`world_frame_core_test.py` 回归原始快照、实际传输/读取会话、Host 显示隔离与原生采样接入。证据为 Linux CPU/受控 Win32 I/O，未测实机端到端延迟、Windows 游戏或联机 FPS。1ms是测试中的提交间隔，不是实际采样延迟保证。
