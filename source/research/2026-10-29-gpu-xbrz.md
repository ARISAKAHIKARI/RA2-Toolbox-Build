# xBRZ 1.9 的 Vulkan 重建：原生输入、两阶段规则与验证边界

用户要求尽量把适合的渲染工作移到 GPU。第一阶段只把 CPU 已重建图像的分数倍率解析交给 Vulkan，冷素材仍需 CPU xBRZ 和较大的上行传输；本次新增从原生 PARGB 输入直接在 GPU 重建的路径。调查前检索 INDEX、持久 notebook v79 与既有 xBRZ/VERA20K 笔记；整体协调器另见 [Vulkan 场景管线](2026-10-29-vulkan-compute-resolve.md)。没有新增游戏地址、原函数调用、Hook 或游戏内存写入，游戏 EXE SHA/ABI 不适用于本项宿主算法移植。

## 算法身份与输入

`third_party/xbrz/` 仍是未修改的 Zenju **xBRZ 1.9**；`xbrz.cpp` SHA-256 为 `882346f5f6703f286c55d4089af7a8f63140fe13a133318e4be64891689bee0c`。来源及全部原文件哈希见 `UPSTREAM.json`，保留上游 GPL 许可。新增 GLSL 是本仓库的 GPL 派生移植，使用上游 `argbUnbuffered`、默认 ScalerCfg、**2/3/4×** 的实际规则；没有加入另一个判边算法，也不宣称实现了上游5/6×或自定义配置参数。

输入是不可变 native premultiplied ARGB8。shader 按现有 CPU adapter 的整数公式转 straight ARGB；透明越界读为0。颜色距离使用上游未查表的 BT.2020 YCbCr/alpha 路径，混色和 alpha marshaling 使用相同无符号整数及四舍五入除法，最后回到 PARGB。重建整数倍率之后，再解析实际目标倍率，因此不是固定2×。

地形保留连续 native canvas 的邻域 halo。SHP 由 `GpuSceneRecord` 先按当前 Light/gains、precision 和 emissive 索引生成 **native 尺寸**着色输入，GPU 执行 xBRZ，不再先生成 CPU 放大图；光照变化不能复用旧着色结果。对象的原始 coverage/Z 仍负责准入，重建不能扩大原生遮挡几何。

## 两阶段与精度

| 阶段 | 工作与写入所有权 |
| --- | --- |
| corner preprocess | `(W+1)×(H+1)` invocation，读取上游4×4邻域，独占写一个打包角点结果 |
| scale | `W×H` invocation，读取四个相邻角点及3×3颜色核，填中心色并依次执行0/90/180/270度规则；独占写本源像素的 `factor²` 输出块 |

两个 shader 共用3个 storage binding（native source、corner flags、reconstructed atlas）与24字节 `gpuxbrz::Params`；偏移单位为 uint32 元素。workgroup 为8×8，边缘多余 invocation 有界检查。一个 compute→compute shader-write/read barrier 分隔两阶段，重建完成再建立供倍率解析/场景读取的屏障；没有不同源像素竞争同一个输出块。

距离和分支要求 `shaderFloat64`。GLSL `precise` 与生成器检查保留 Float64/NoContraction，避免换用 FP32 或 FMA 收缩改变判定。生成的 preprocess/scale 分别有242/259个 NoContraction decoration。这仍不能证明所有硬件的 sqrt/divide 与 CPU 对全部输入都逐位相同。

`FrameResolve::verifyXbrz` 在设备首次 raw reconstruction 前，将固定7×7输入的2/3/4×结果放进同一个63×28 GPU frame，与由未修改 CPU xBRZ 生成的 golden 比较；checked/running/rejected 状态防止递归与重复初始化。不一致时拒绝该 raw reconstruction 路径并回退。它只是一组有限设备自检，不是全输入精度证明。测试还先验证这些 golden 与当前平台编译的原上游实现一致，防止把生成器平台差异误当作 GPU 差异。

## 常驻缓存与提交

`vulkan_xbrz_backend.h::Stage` 的 raw source atlas 上限 **96MiB**，输出写入协调器已经预留的色图集区域（整体上限128MiB，另计 scratch/staging 等资源）。raw cache 比较 weak shared ownership、对象地址和尺寸；地址重用不会命中旧内容。同一不可变源的2/3/4×重建共享 raw 上传，输出缓存则另含尺寸/倍率签名。SHP native 着色缓存同样区分原 Image owner、gains 和 precision，并有4M native像素/128项上限。

`prepare` 规划空隙/必要的有界重排并暂存缺失源；`record` 批次复制、preprocess 和 scale，**不自己 submit/readback**。仅完整帧 fence 成功后 `commit` 才发布缓存身份。放弃录制不能将未完成输出当作已缓存。结果直接供下游倍率解析和场景使用，正常帧只有协调器的最终回读批次；GPU 不可用、精度/尺寸不支持或执行失败时保留原 Surface 同帧 CPU 重播。

- Bootstrap **40743255379**，head `deb54f6c8c649fb26dff3e8c791b7f267e3c6b7b`，job `123010185357`：官方 glslang/spirv-val、ASan/UBSan及 Khronos validation 下，`gpu_xbrz.cpp --require` 在 **llvmpipe LLVM20.1.2** 实际 dispatch/readback通过。190输入、589帧、**8,167,384像素完全一致**，570 fresh builds，16 warm frames上传0/重建0，正常帧最终回读1。包括透明/近似色、单像素/单行/单列、细线/孔洞/旋转、随机输入、实际262×262 halo tile，以及同地址不同 owner。
