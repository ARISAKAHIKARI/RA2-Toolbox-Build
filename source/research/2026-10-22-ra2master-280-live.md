## 有壳，且与本轮采集为同一 EXE

- Detect It Easy 3.21 命中 **VMProtect 2.0.3–2.13** 签名。此范围是识别器结果，不是精确保护器版本的证明。
- EXE 大小 7,061,504 字节，入口 VA `0x11F8066`；磁盘 `.text/.rdata/.data/.kkqy0` 原始大小为 0，主体集中于高熵 `.kkqy1`。不是未加壳版本。
- EXE SHA 与采集报告完全一致，也与此前 2.90 分发包中的“控制别人坦克卖别人建筑辅助.exe”一致。新附件及运行时标题支持把该样本识别为 2.80；不再仅以辅助程序文件名推断版本。
- 包内说明称：先勾选“控制全部”，再用 Alt+1～8 切换玩家；切换会取消控制全部，并注明切换用于联机。这里只记录包内说明，尚未验证功能或同步行为。
- 实机映像的部分代码、字符串和数据已经展开，仍有函数跳入 VMProtect 区域，不能把主模块 dump 称为完整脱壳 EXE。

## 采集覆盖与差分

- 游戏主模块基址 `0x400000`、大小 7,942,144 字节，四阶段都完整读取。修改大师主模块大小 14,958,592 字节，也完整读取。
- 未启动→启动但关闭：游戏 VA `0x577B3A` 的 `74`→`75`，即同一短跳转由 JE 改为 JNE。两个阶段相隔约 536 秒，不能仅凭相关性认定写入者或用途。
- 控制全部关闭→开启→关闭：可执行节变化均为 **0**。没有独立的出售功能采集。
- 数据段共有 8 个稳定且可恢复的单字节候选：`0x87E7A0` 的 E9→E8→E9（所在 DWORD 为 1001→1000→1001），以及 `0xABDA97/9F/A3/A7/AB/AF/C7` 的 0F→0E→0F。后一组位于其他字节也在改变的 DWORD 中，不能当作控制开关。
- 两次游戏私有可执行区域列表均为空。工具没有保存普通游戏堆，也没有保存修改大师堆；零代码差分不能排除数据写入、瞬时写入、其他模块修改或目标进程不一致。

## 用户更正：9544 是 explorer.exe，变量用途仍需追踪

- 采集记录的游戏 PID 是 **29604（0x73A4）**；修改大师 PID 是 28900。
- 修改大师映像 `DWORD[0x631C84] = 9544（0x2548）`。可读的选中对象处理函数将它作为第一个参数传给 `0x4022EE` 和 `0x402413`。
- `0x4022EE` 为 DWORD 读取包装器，stdcall 四参数、`ret 0x10`：参数 1 不是 -1 时，按 `OpenProcess(0x1F0FFF, 0, arg1)` 的参数形态打开进程，再调用 ReadProcessMemory 读取 4 字节并关闭句柄。
- `0x402413` 为 DWORD 写入包装器，同样以参数 1 打开进程，写参数 2 地址处的参数 3 DWORD。
- 用户随后明确指出 **PID 9544 是 explorer.exe**。这是用户提供的进程身份信息，采集包未记录该 PID 的身份和时间，不能独立复核。撤回“可能是另一个游戏实例”的解释；不能把这一变量直接称为修改大师当前控制功能的目标 PID。
- 目前只能说：在捕获瞬间，该槽位为 9544，可读的选中对象处理路径把它传给远程读写包装器；尚未证明控制全部开关在采集时实际执行该路径，也未确定槽位最后由谁写入。不能据此宣称修改大师注入 explorer、通过 explorer 转发、读错游戏，或把零差分归因于进程不一致。
- 追加静态检查：整幅主模块中该地址的 507 次直接字节引用均为 `FF 35 84 1C 63 00`（push DWORD[0x631C84]）；大量位于受保护区。没有找到直接编码该地址的写指令，但间接寻址/虚拟化代码仍可写入，不能据此说变量未更新。
- 选中对象函数的三个可读调用点是 `0x401F4B/0x40304D/0x40611E`，均受另一个 UI ID `0x160232B4` 的属性判断约束；这进一步要求区分选中对象修改功能和 ControlAll 配置关联回调。未还原完整调用链。

## 已可读的实现片段

以下地址均属上述修改大师内存映像，不能直接当作游戏补丁地址。

- `0x4A2EA4` 是 `ControlAll` 配置键。设置加载和保存路径关联 UI ID `0x16026C49` 的属性 `0x12`。`0x406336` 读取/翻转该状态并在 `0x406374` 调用 `0x403964`；后者跳往 `0xB4342A` 受保护代码。它是配置关联回调线索，尚未还原其实际写入。
- 可读函数 `0x401F59` 从全局地址表取得游戏选中对象数组 `0xA8ECBC`、数量 `0xA8ECC8`、CurrentPlayer `0xA83D4C`。其中一个分支跳过特定 vtable 后，把当前 House 指针写到选中对象 `+0x21C`。这证明样本包含选中对象所属方修改路径，**未证明控制全部开关使用这条路径**。
- 地址表中也有 `0x50B652/0x50B6F7/0x6D88FC/0x577B3A` 等游戏地址。只找到地址常量不能确定对应功能或实际使用的补丁内容。
- UI 资源反复出现的 `0x160186BD` 是可重复组件标记，不能据某一次相邻字符串把它当作控制全部的唯一 UI ID。

## 受控回调尝试及剩余工作

用 Unicorn 2.1.4、Capstone 5.0.6 映射主模块和合成栈，尝试从 `0x403964` 跟踪。两次预设不同 UI 状态的尝试都在到达 UI/API 模型之前停止：PC `0x672AD3` 读取未捕获的 `0x0153B914`，触发 `UC_ERR_READ_UNMAPPED`。缺少模块外数据；不能把这两次尝试描述为已经执行了开/关逻辑。

下一步先确认用户所说“可运行”是否包括实际选中/移动敌方单位；追踪实际 ControlAll 回调、有效 API 参数和 PID 槽位的写入来源。推进回调需要补采修改大师相关堆区/私有内存；现有工具重复只抓主模块无法解决缺失数据问题。
