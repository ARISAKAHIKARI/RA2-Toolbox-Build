# 主动快捷键回归源头：从 1.0.43 到 1.0.46.4

## 结论与前一轮归因修正

用户补充：尚未试用 1.0.47-pre.4；问题是在最近 Hook 依赖与性能优化后新出现，1.0.43 应没有同样症状。本轮以正式发布源码回溯，不能把用户的版本印象替代同机 A/B，也不能把一个源码反例当作该现场的唯一根因。

**已经确认的新回归来自 1.0.44-pre.2 的共享世界采样迁移 `944586abf9cd331d2aaf9fe24af744a593bd31d3`：采样上游依赖和失败语义发生变化，连接启动与快捷键准入仍保留旧的显示依赖。** 这形成了可复现的特定配置冷启动循环，并新增了两个时钟混用的短暂误失效条件。

需要修正上一轮说明：`snap.renderStatus==1` 门槛、普通键依赖 `WM_HOTKEY`、系统注册失败丢弃绑定，在 1.0.43 已经存在。pre.4 修掉了真实的公共阻断点并加强输入恢复；这不能证明该门槛是最近新增，也不能证明上传日志的现场问题已经闭环。

上传日志里桥接已经连接、命令状态就绪且完整显示发布路径持续执行，因此本轮复现的冷启动循环不满足该段现场的前置条件；混合时钟反例也不能单独解释几分钟持续失灵。现场具体是显示候选无效、聊天状态、配置或注册问题，旧日志没有足够观测值唯一判断。

1.0.43、1.0.46.4、pre.3 的 `hotkey_host.h` 和 `hotkey_routes.h` 各自逐字节相同。`main.cpp` 中 `desiredHotkeyMode`、`registerKey`、`registerKeys`、同步、前台检查及只读按键路径等九个函数也相同，消息循环没有删掉热键分派。记录见 [registry-history.json](evidence/pre147-hotkey-origin/registry-history.json)。

因此，最近删除普通键轮询、最近新增显示门槛、最近删除 `WM_HOTKEY` 处理等说法被历史源码否证。系统消息后备是合理加固，但没有证据把它当作这次新增回归的来源。

`runtime_feature_demand.h` 在两个正式版本中逐字节相同，冷启动反例也使用了这份相同的生产判断。1.0.46.4 控制台提交的实际新增/删除行也未修改热键编码或键值写入。不能笼统归因为 Hook 被优化掉了。

## 二、真正新增的依赖关系

1.0.43 的 `sampleExternal` 可以先通过外部进程读取形成有效显示数据。旧 `needsBridge` 见到 `externalData->status==1` 后建立命令连接。后来即便保留了错误的显示准入条件，在常见正常读取情况下也不一定暴露。

944586 把显示读取改成以下规则：先取得 `WorldFrameScope`，从封口的共享原始页读取；必需缺页使本次不完整；没有样本或本次不完整时提前返回，保留旧发布；完整后使用原 producer 的采集时刻发布。跨进程样本、字段完整性和订阅恢复从此成为显示发布的前置条件。

但旧连接判断和旧快捷键判断没有同步调整。显示就绪因而承担了三个不同职责：画面是否可用、是否应启动 Runtime、主动按键是否可进入命令通道。迁移改变了第一个职责的前置条件，后两个消费者仍依赖它。这是本轮确认的设计缺口。

## 三、确定回归 A：特定配置的冷启动循环

前提必须完整保留：工具箱启用且游戏在前台；外部读取有效；尚无 Assist 桥或其他模块提供可接受的世界样本；关闭其他持续 Runtime 需求；清空默认“攻击脚下”快捷键，只保留基本手动快捷键（本例保留 Ctrl+Alt+L 的 AutoBoard）；没有排队命令、选择请求、调试页或闪烁任务。

此时新代码出现闭环：没有 Runtime 连接就没有世界样本，没有世界样本就没有有效外部显示数据，没有有效显示数据且无其他需求就不调用 `ensureBridge`。基本主动键又未注册，无法靠按键进入能主动连接的 `send()`。

这不是开箱默认配置：默认“攻击脚下”绑定 Ctrl+Alt+F 本身属于 Runtime 需求，会打破循环。开启自动修理、已经有连接或已有其他有效 producer 也会改变条件。直接点击走 `send()` 的 UI 命令有独立连接机会，不在本反例的断言范围内。

实际提取五个版本的完整 `sampleExternal`、`mergeExternal`、命令身份与注册函数，保留 tick 内“注册检查→采样→needsBridge”的原始语句顺序，连续执行十二轮。共 **20 个场景、164 项检查**，编译和运行均成功；独立复核确认提取函数、调用点和日志摘要一致。

| 版本 | 仅基本手动键：连接调用次数 | 显示采样调用次数 | AutoBoard 注册 |
| --- | ---: | ---: | --- |
| 1.0.43 | 1 | 12 | 成功 |
| 1.0.44-pre.2 | 0 | 0 | 未注册 |
| 1.0.46.4 | 0 | 0 | 未注册 |
| 1.0.47-pre.3 | 0 | 0 | 未注册 |
| 1.0.47-pre.4 | 0 | 0 | 未注册 |

后三个阳性条件——默认攻击脚下绑定、自动修理需求、预先连接——在五版全部恢复。新链路在失败场景十二次尝试世界读取，十二次均不可用，没有一次连接尝试。详见 [bootstrap-result.json](evidence/pre147-hotkey-origin/bootstrap/result.json)。

夹具使用受控 Win32、成功外部读和 IPC 边界，连接调用后立即允许 IPC。公共支持头绑定当前精确源码，需求与默认设置头另与 1.0.43 原始字节核对相同。它执行的是历史 Host 生产函数与这些边界的组合，不是完整旧版产品、真实 Windows 按键或游戏指令执行。

## 四、确定回归 B：producer 时钟与显示时钟混用

1.0.43 的显示采集时间和年龄比较都使用 Host 的 `sampleRenderClock`。944586 把样本时间改为 Runtime `GetTickCount()`，而 `mergeExternal` 仍用 Host 的 QPC 插值显示时钟相减。

每轮采样先将 `externalSourceConfirmed` 清为 false；没有 token 或必需缺页时会提前返回。后续快照合并如遇 producer tick 暂时领先 Host 显示钟，无符号减法就会把几毫秒差异当成巨大年龄，令 read/render 状态归零，再被旧热键门控解释为禁用。完整样本的 `externalSourceConfirmed=true` 会正确绕过年龄限制，不能忽略这层保护。

实际提取两版的年龄/read/render 语句和 `desiredHotkeyMode`，用受控时钟编译执行 **11 个场景、33 项检查**：

| 条件 | read / render | 热键模式 |
| --- | --- | --- |
| 旧版同一时钟，now=1000、tick=1000 | 1 / 1 | 2 |
| 新版 now=1000、producer tick=1008，未确认 | 0 / 0 | 0 |
| 相同未来时间戳，来源已独立确认 | 1 / 1 | 2 |
| Host 时钟追到 1008，未确认 | 1 / 1 | 2 |
| 真正超过 2000ms，未确认 | 0 / 0 | 0 |

8ms 是人为设定的模型输入，不是现场实测偏差。`uint32_t(1000-1008)` 为 4294967288，产生了确定的错误年龄判定。单次误判随 Host 显示钟追上而结束；它能够造成短暂注销与丢按键，但本轮没有证明反复出现的时序吞掉了用户所有输入。详见 [mixed-clock-result.json](evidence/pre147-hotkey-origin/mixed-clock/result.json)。

## 五、已经排除和仍未证明的说法

上传日志的 258 条存活 PID 健康记录全部 `commandStatus=1`，255 条 fresh=1，`request=ack=5` 不变；native/click Hook 均为 1，错误和拒绝计数没有增长。这支持“没有新的主动命令跨过提交边界”，不支持“命令发出后被自动装算法拒绝”或“游戏 Hook 全部停止”。

63 条真正的 `display ... samples=` 记录，中位计数为 291。该计数位置在 `worldScope.complete()` 通过之后，因此不能说整段时间共享世界始终没有发布。`information-sample` 的函数 Scope 调用数则包含早退，不能用它替代完整路径计数。完整返回的候选仍可因 viewport、layout、House/type 等条件而 status/renderStatus=0；旧日志没有记录这些值。

旧 `bridge-health renderStatus` 实际是 `incoming.renderRevealStatus`，不是 `snap.renderStatus`。全为零不能用来直接证明这次显示门控触发；labels=0 也不能证明同一结论。原始用户日志没有提交，本轮仅复核其已记录 SHA256 和派生计数。

还发现同一 token 快路径只刷新相机而不重读全部 visibility/layout/viewportKnown 的状态滞留边界；这需要同帧条件，现场控制帧持续前进，不能拿它单独解释整段故障。逐次 subscribe/acquire、失败缓存复位和 RAII 需求提交均存在，没有发现“一次缺页就永久停止”的锁存。

## 六、pre.4 的实际覆盖与修复要求

pre.4 已切断“显示失败→主动快捷键禁止”的错误依赖，注册和分发改看命令上下文；普通键采样后备和去重属于额外输入恢复。因此它对已连接且显示失败的路径有明确覆盖。

pre.4 没有改变 `needsBridge` 冷启动判断，也没有消除上述显示时间戳混用；本轮复现明确保留了这个未修结论。不能将 pre.4 的输入测试通过扩写为所有近期优化回归都已解决。

完整修复应分别处理：连接启动由功能/命令意图决定，不等显示发布；主动键只依赖真实命令权限与输入状态；显示年龄使用同一时钟域或显式转换；共享样本失败影响它的消费者，不扩散成所有手动功能失效。回归检查必须把首次连接、缺样本、恢复、显示不可用但命令正常串在同一条实际 Host 路径里。已有单独的需求表达式和显示/手势测试不能替代这个组合。

本轮只确认 Host/采样的源代码回归和受控反例，没有新增游戏地址、原生 ABI 或受支持 EXE 身份结论。没有真实 Windows、现场游戏或联机验收，也未从现有日志唯一确认持续失灵的最终触发字段。已交付二进制仍以原来的固定源码提交与发布 manifest 为准，本记录不重写当时的构建或测试事实。
