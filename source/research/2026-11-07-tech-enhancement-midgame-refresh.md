# 科技加强：中途开启后的原生重查与有效目录刷新

## 问题与来源

用户反馈：科技增强在游戏中途开启后仍无法建造，怀疑缺少建造栏刷新。本轮从已发布 `1d7f3020b12c8f25b8b83e161ddd1bafc6364cda`（1.0.43-pre.3）检查两个独立实现。先读 INDEX、[精确科技等级参数](2026-11-03-tech-enhancement-exact-parameters.md)、[数据模式审查](2026-11-01-control-tech-data-only-review.md)和已有原生侧栏／生产记录。持久笔记已检查；其中没有这两个指定科技笔记条目，采用仓库记录。

本轮没有用户游戏日志，也没有启动私有游戏映像。下面的反例是生产函数抽取后在合成内存中复现的刷新缺口，不能替代用户环境中的实际侧栏／生产验收。

## 两条确认的缺口

旧规则模式在确认白名单 Type 的科技等级写入成功后，会重扫工具箱目录；但独立开启加强、没有同时开启科技全开时，不会请求游戏重新检查建造树。冻结 pre.3 的 BUS 反例中，原值 -1 已改成 1，工具箱目录已收录，`House+0x1FC` 仍为 0。缺少的是原生刷新请求，不是再次写科技等级。

精确模式保留实际规则值，原生类型数组的地址、数量与 stamp 在开启前后可以完全相同。此前扫描将 TechLevel=-1 类型过滤后，中途启用虽已捕获加强策略，`typeSlot(type)` 仍可能找不到该类型，导致在原生可建造探查和 AddCameo 之前退出。冻结 pre.3 的第二个反例明确观察到这种“策略已准备、目录仍缺项”的组合。

## 有限修正

`tech_enhancement_bridge.h`：仅在本轮确实新取得 TypeLevel 写入所有权时，通过现有字段请求一次 `House+0x1FC = 1`。没有变化的后续扫描不会重复请求。保留大师模式既有自然刷新策略，但判断必须是 `techImplementation==2 && (snap.techOpen || techPending)`；只在下拉框选中大师、实际全开已关闭时，不应压住独立科技加强的刷新。

`tech_ui_breakpoint_bridge.h`：加强请求的开／关边沿标记目录失效并调用现有 `scanTypes()`，使有效科技等级过滤结果及时更新。有全开时复用既有 `requestTechRefresh()`。后续图标插入仍先核对签名、世界身份、硬件就绪、原生可建造、真实工厂及页容量。既有新世界／重置路径会重扫目录，函数内请求边沿状态不会替代那些生命周期检查。

保持原来的 21 类白名单与 insignificant／spawned／owner 筛选；没有新增生产绕过、Hook、协议字段或队列清理。正在生产／排队的类型仍使用原有双向权限交接。旧规则模式仍是既有共享规则数据实现，本次只补刷新；精确模式仍不写 TypeLevel。

## 原生依据与未重新证明的边界

沿用既有支持映像 SHA-256 `268a81b7422b3bb855e1b4a162aadba4d807f88fb9f70feb99118211d8fbb8d0`；本轮未重新校验／执行该映像。既有记录将 `House+0x1FC` 标为一次性 RecheckTechTree：`0x4F9265` 读取、`0x4F927C` 清除，并配合 Building `+0x4E0` 枚举。它是重查请求，不是无条件解锁。

原生 Produce `0x4FA350` 经 FindFactory(false,true,true) 和 CanBuild(type,true,true) 保留真实工厂、国别／所属、海陆、供电与数量条件。精确模式既有 CanBuild `0x4F7870`、Jcc `0x4F7951`／`0x4F7B66`、限定 UI 返回 `0x6A97D7`／`0x6AA786` 以及受控自有 probe 均未新增或放宽。AddCameo `0x6A6300` 继续使用既有原生路径。

排除“清空生产队列以迫使重建”“放开所有特殊类型”“增加新的生产拦截”三种方案：已确认的失败发生在刷新调度和本地目录过滤，现有生产条件不需要改变。

## 验证

[前后对照证据](evidence/tech-enhancement-midgame-refresh-20261107.json)来自 `assist/tests/tech_enhancement_midgame.py`／`.cpp`。两个冻结 pre.3 反例分别绑定准确失败信息，不能把任意编译／执行失败当成复现；修后 19 个场景／55 项检查通过。覆盖中途开启、无变化不重复请求、请求关闭再开启、异步就绪、实际 stamp 不变、完整白名单、原生拒绝、缺工厂、页满、签名失败、大师实际启用／待启用／仅选择但关闭，以及在产模式交接。合成工厂、产品与队列字节在执行前后保持一致。

原有 `tech_enhancement_world.py` 仅补刷新字段写入和全开状态的模型定义；其 34 项世界身份／恢复检查再次通过。该轮使用原 runner 生成的 C++，由 Linux g++ 适配编译执行，断言启用。

这些检查运行实际抽取的激活／还原／目录过滤／图标门控函数；原生资格、工厂、AddCameo、签名和硬件就绪调用为明确模型，内存为私有合成数据。未执行真实游戏指令，也未运行本版 Windows 程序。最终同提交完整构建、PE／版本／成套附件校验单独记录在本版 `release-manifest.json`；真实建造栏、点击生产、特殊 MOD 和联机行为仍需实机验收。
