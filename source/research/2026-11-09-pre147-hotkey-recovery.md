# 1.0.47-pre.4：自动装车及主动快捷键的共用输入恢复

## 现场证据和结论范围

用户报告“自动装按了没反应，所有需要快捷键触发的功能都不灵”。上传的 `Runtime.log` 共 898 行，时间为 2026-11-09 14:41:21.947 至 14:50:47.480；文件标记 `v1.0.46`，该标签不能区分 1.0.46 与 1.0.46.4。

游戏运行期间，桥接、回调与逻辑帧仍在推进，`request=ack=5` 一直不变，原生命令队列累计量从 805 增至 1075，队列满、提交拒绝、Runtime 错误和故障序号均为零。63 条展示状态中 59 条为前台。第 721 行明确记录游戏在 14:46:45.599 正常退出；之后的 no-target 和重连失败不能解释退出前的快捷键无响应。

这些证据将检查范围收敛到主动命令发布前的共用入口。它们不能证明某个实体按键已经被捕获，也不能证明现场唯一原因。原来的 `bridge-health renderStatus` 实际指 `incoming.renderRevealStatus`，并非外部画面就绪状态，不能拿其中的零值当作本次门控的直接现场证据。零标签也不能证明画面采样失败。

派生计数与日志 SHA256 见 [runtime-log-summary.json](evidence/pre147-hotkey-recovery/runtime-log-summary.json)。没有将完整用户日志、游戏可执行文件或内存转储提交仓库。

## 1. 命令输入错误依赖展示采样

旧代码的 `desiredHotkeyMode()`、`handleHotkey()` 和 `serviceHotkeyBatch()` 均要求 `snap.renderStatus==1`。该值来自外部展示采样：视口映射暂不可用、布局探测尚未完成或展示样本不足，都可能使它为零，即便 Runtime 的命令权限及连接完全正常。结果分别为注销命令热键、丢弃已收到的消息、清空等待动作。现有 gateway 单测只验证合并状态，没有覆盖三个实际入口，因此漏掉了这个重新引入的展示依赖。

现在三处使用同一 `commandHotkeyContext()`，由启用状态、游戏前台、Runtime 命令权限和聊天状态决定。注册保持正常命令身份，不因一段延迟反复解绑；实际分发继续检查原有 1500 ms 新鲜度。真正暂停、菜单和隐藏游戏仍由 Runtime 发布的 commandStatus 拦截。只读副屏跟踪继续使用独立的展示条件；放置、队形和鼠标坐标相关功能保留自己的视口、所有权与输入时效检查。

自动装车本身的路线没有改变：热键 1011 或按钮 111 → `actions[11]` → `AutoBoard`（15）→ 原有 `send()` 和 Runtime `autoLoad()`。因此本次没有修改装车分配算法、原生命令类型或游戏内/工具箱计算选项。日志的 `computeApplied=0x1FA0` 已置 Load bit，按现有 compute 策略表示该功能在游戏内计算，不能误写成工具箱计算故障。

## 2. 普通键缺少检测后备与双通道去重

旧采样器只为鼠标和裸修饰键生成按下边沿，普通键完全依赖 `RegisterHotKey` 和 `WM_HOTKEY`。系统注册失败时，旧 `registerKey()` 直接丢弃整个绑定。现在保留该绑定并记录系统错误，利用现有前台采样器识别普通键的实体按下边沿；不增加注入入口、低级键盘钩子或游戏内逐帧工作。

系统消息与轮询共用 Registry 手势状态。`message()` 使用实际消息时间、已消费边沿以及已观察的释放边界，处理先消息、先轮询、消息稍晚入队和释放后迟到消息，避免一次按键执行两次。消息仍能补足采样间的短按。首次同步、失焦、聊天、暂停、连接失效和换局会设置取消边界，恢复时仍按住的键须释放后重新按下；过期消息不能跨上下文重放。修饰键失效后也不能通过重新按住修饰键复活旧的主键；未配置的 Windows 修饰键也不会触发普通命令。

独立复核还用真实 Host 入口复现了新后备路线的收尾问题：Host 停顿 501 ms 后，旧的持续按下可能被误作攻击脚下的新输入。最终版本保留最近物理采样时刻；没有已知采样时间或间隔超过 150 ms 时，攻击脚下、自毁所属方和建筑放置均拒绝该边沿并提示重新按键，不能因备用采样绕过它们原有的即时性约束。普通自动装车仍可按原命令策略处理。这个时效条件应用于真正的即时 consumer，不改变普通命令与 ACK 队列。

仅凭离散状态不能区分所有极端事件组合。例如第一次系统消息完全丢失，同时释放与第二次短按也全部位于两次采样之间，可能与第一条消息稍晚入队产生相同观测；该不可区分边界优先避免双发，不宣称任意短于采样间隔的手势都已获得无损捕获。

参考的 Win32 契约：Microsoft [RegisterHotKey](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-registerhotkey) 与 [GetMessageTime](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getmessagetime)。消息时间是入队时间，因此不能假定它总早于首次轮询看到按下的时刻。

## 3. 可区分输入与执行的日志

Runtime.log 新增配置热键被拦截的原因，以及普通主动命令的提交与结果。周期健康记录新增真正的 `displayRenderStatus`、热键模式、绑定组数量、待处理动作、消息/采样/动作计数和系统注册失败信息。每条消息、分发、执行等细分记录只在开启诊断时写入 Assist-debug.log，避免为一次普通按键额外同步写入多条常规日志。

日志仅记录配置动作边沿和命令结果，不记录每次键盘采样，不在游戏异常或输入钩子中写文件，沿用 Host 侧有界日志轮换。

## 验证和未决项

`assist/tests/hotkey_command_context.py` 执行真实 Host 身份、注册和分发函数，最终 `send()` 接收端及 Win32 为受控边界。用 pre.3 的真实函数替换时，三个展示门控分别出现预期运行失败；不能以提取或编译失败冒充负对照成功。当前版覆盖展示失败时 AutoBoard、系统注册失败后的采样后备、按住不重复、命令/选择 ACK 串行，以及暂停、菜单、聊天、失焦、过期和恢复。

`assist/tests/hotkey_message_recovery.py` 和其 C++ 用例验证真实 Registry 的双通道顺序、短按、双击、释放、过期、取消、换局与时钟回绕，并保留旧 header 无系统消息时零触发的负对照。既有手势和发布专项继续执行。最终回执记录实际命令、返回码、当前源码摘要；构建及包校验由同批交付的 manifest 绑定。

本次是工具箱 Host 输入代码的修复，没有新增游戏入口地址、ABI、字段偏移或受支持游戏 EXE SHA256 结论。沿用 1.0.46.4 产品基线以及 pre.3 功能修复，Assist102/Cursor155/Runtime4 协议布局保持不变。以上受控执行及 Windows 目标交叉编译不等于原生 Windows、实际装车、物理 GPU 或多人联机验收；现场唯一触发条件仍需新版日志才能确认。
