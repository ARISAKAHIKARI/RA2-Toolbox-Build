# Hotfix29 后的性能回合：保留已确认可用的框架，逐项验证

用户实机反馈：Hotfix29 致命问题已修复，性能仍有明显缺口；要求逐步分析此前回退的部分能否合回。这是用户反馈，不扩张为所有游戏/平台/显卡均已验收。

交付基线为远端 `60fc8a3411a4d3ec68c75cabc1486a2a0257f9b5`（本地 `84c78b52cd90de8dcfb7f7ac1bb241537b6a89b4`）。本次候选在独立 `codex/render-performance-step1-20261031`，交付分支和 Hotfix29 更新包不变。调查前查阅 INDEX、HF28 自审、HF29 恢复记录及同一 SQLite 笔记 v107。

HF29 同时改变多个环节，恢复可用并不能证明某一个被撤回模块就是唯一故障原因。每次只恢复一个可隔离的变化，保留完成帧、失败保持和退出约束。

## 回退内容的逐项判断

| 内容 | 当前判断 | 合回条件 |
| --- | --- | --- |
| 常驻世界输入、素材与姿态缓存 | 多数已经保留，不应重复移植 | 找出现有失效/重复准备的具体调用，再缩小重建范围；保持可见性、材质、光照与姿态验证 |
| 第二个异步呈现工作线程 | 暂不恢复 | 先把可复用的准备结果在当前单一绘制者内复用；证明配置/快照/资源生命周期后才拆线程 |
| CPU 输出行分片 | 暂不恢复整段旧实现 | 完整图像/附件预处理只做一次，普通绘制按行独占；位移和读取目标内容的效果是同步边界；ARGB、float-Z、u16-Z、A、缩放及附件共同验收 |
| Vulkan/D3D11 共享纹理与 DirectComposition 直出 | 潜在收益大，但后置独立验证 | 证明跨 API 所有权、keyed-mutex 时序、最终呈现、模式切换和退出；场景生成捕获异常不能代替这些证明 |
| CPU 清屏/底图/深度的冗余初始化 | 第一项小型候选 | 不改变绘制顺序与目标读写，只省掉确定会被覆盖的内存写；先做基线对照 |
| xBRZ、超分、颜色增强 | 低优先级 | 基本画面与吞吐达标以后再考虑；继续尊重用户允许删除这些功能的要求 |

参考仍固定为 `vera20k@3d42426b2e9c1b4cf913a7dbbaaf8bf7d3b6bc7f`。本轮主要审查自己的回退差异，不把保留了几段代码写成已经完整迁移 Vera，也不把 CPU 回读称为 Vera 日常呈现方式。

## 第一项候选及测量

旧 CPU replay 先 `Surface::reset` 清空颜色/float-Z/u16-Z，再覆盖底图，原生 A 初始化时再次清 Z，最后再覆盖基础 float-Z。

候选 `resetFrame` 直接装入已验证的完整底图/基础深度。紧凑深度只调整向量长度，随后在绘制前覆盖全部元素；A 初始化保留其颜色运算，但不再次重置已经准备好的深度。u16-Z 仍从 FFFF 开始。普通 `Surface::reset` 和其它 `nativeBase` 调用的默认行为保留。没有改对象先后、像素算子、GPU 路径、呈现或帧保留窗口。

`assist/tests/frame_replay_initialization.cpp` 对 HF29 与候选分别编译，32 种 native/float、紧凑/完整 Z、A、位移、延迟底图组合的 ARGB/float-Z/u16-Z/A 摘要相同。每种组合破坏原 Surface 尺寸后再次回放，结果相同。另通过 HF29 `render_recovery` 和 36 组 `gpu_scene_record` 的 CPU 重放检查，没有创建 GPU 设备。

六轮顺序为 baseline/candidate/candidate/baseline/candidate/baseline；每轮先暖场 3 次，再取 15 次 replay 的中位数；表中为各变体三轮中位数的中位数。计时不含准备输入、绘制窗口或游戏读取。所有计时场景包含原生 A 遮罩（值遍历0..127），所以零物件用例也有整帧遮罩运算，不是纯 memcpy 微基准。环境为本机 CPU 合成场景。

| 输出 / 物件数 | HF29 replay | 候选 replay | 变化 |
| --- | ---: | ---: | ---: |
| 1280×720 / 0 | 7.180 ms | 5.813 ms | 减少 19.0% |
| 1280×720 / 160 | 12.622 ms | 12.820 ms | 增加 1.6%，没有稳定收益 |
| 2560×1440 / 0 | 29.510 ms | 26.072 ms | 减少 11.6% |
| 2560×1440 / 160 | 36.248 ms | 32.954 ms | 减少 9.1% |

这是候选中一个明确的重复写入优化，收益不是所有场景一致，更不能解释或承诺消除用户此前的约250ms问题。因此保留在独立性能分支，不替换已经实机确认的交付。完整轮次、摘要和测量范围见 `evidence/frame-replay-initialization-step1.json`。

## 当前更值得追查的准备成本

1. `radar_scene.h` 的 prepareWorldOnly 路径在准备世界快照之前仍创建 `nativeBase=background_.fork()`、`view=nativeBase.fork()`。两者在该路径的后续绘制分支均未使用，然后 packet 又复制一次 ground。`fork` 共享像素页，但会复制整个 `std::map` 页索引与容器节点。这是可定位的冗余源代码路径；尚未测出其占比，下一轮优先隔离验证。
2. CPU 原生场景仍建立 GPU 命令记录，最后再做 CPU replay。不能简单删掉记录：当前完成帧比较依赖完整的材质/Z/A/特效输入。需要拆开“比较键”和“GPU 专用准备”，而非按游戏帧号复用旧图。
3. 合成器在没有新世界图时仍按目标频率提交同一完整 HWND。减少重复提交可能节省呈现线程，但应先测最终提交成本并验证恢复/移动/反馈；提交同一旧图次数不等于新世界帧率。此轮未改动该策略。

## 证据边界

本轮没有新的游戏逆向地址、ABI 或字段偏移，没有执行或重新反汇编私有游戏。既有资料的样本 SHA-256 `268a81b7422b3bb855e1b4a162aadba4d807f88fb9f70feb99118211d8fbb8d0` 仅作历史关联。拒绝将“所有性能差距来自回读”、行分片必然更快、第二线程必然更快、两个后端相等即原生等价等猜测当作结论。

本轮的 Windows 生产交叉编译/静态检查以分支附带记录为准；没有游戏、GPU 驱动、联机、真实呈现或 FPS 测量。正式 latest 仍为 v1.0.38。
