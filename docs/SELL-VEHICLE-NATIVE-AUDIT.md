# 卖车、围墙覆盖图与退款核对

适用对象：v1.0 的现有卖车入口，以及本次提供的两份 `gamemd-spawn` 静态程序。此文不把静态程序的行为推广到所有红警 2、尤里复仇或加载了扩展 DLL 的版本。

## 当前可以确认的行为

现有工具没有固定“半价卖车”的算法，也没有直接改钱。它经过唯一的 GameRuntime、对象与所有权校验、原版 `Sell` 构造器，以及统一的单机/多人队列提交对象出售事件。退款由接收端执行原版出售和退款函数计算。

在用户提供的程序中，执行原版接收分支、`Foot::Sell`、`Techno::GetRefund`、类型退款函数和 `House::GiveMoney`，得到以下结果。测试设定造价 900、`RefundPercent=0.5`、国家和工厂价格倍率为 1，目标为本玩家的合法战车且所在格有建筑。

| 类型的 Soylent | 原版实际增加的现金 |
| --- | ---: |
| 0 | 450 |
| 900 | 900 |
| 300 | 300 |

因此，“工具卖车固定半价”和“只有覆盖图事件才能全价”都不成立。`Soylent` 非零时走该类型的原版回收价值分支；未设置时，当前测试中的本玩家退款才使用 `RefundPercent`。MOD、国家价格和扩展逻辑可能改变最终值，不能把这里的 900 当成所有游戏中固定的 100% 返还承诺。

## 围墙用法为什么还不能算已经接入

核对时必须区分以下三件事：

| 环节 | 已核对的实现与边界 |
| --- | --- |
| 围墙卖出光标 | 原版的围墙判断可以在同时命中另一个对象时仍给出出售光标；这不证明收到事件后一定会出售该单位。 |
| `Sell` 对象事件，0x16 | 原版点击分支在命中对象时构造此事件。工具现有卖车也使用它。两份静态程序的接收分支均检查归属；车辆还调用所在格的建筑查询。 |
| `SellCell` 格子事件，0x17 | 没有对象时的围墙分支使用它。在本次原版接收代码测试中，它移除围墙，不调用车辆出售，也没有给该车辆退款。不能仅因名字带 Cell 就把它当成“全价卖车事件”。 |

“只有围墙、没有建筑”是需要单独复现的场景。当前两份静态程序的这条 `Sell` 分支在该场景中未调用车辆出售。这里只确认该分支的测试结果，不否定其他游戏版本或运行时扩展中存在围墙错位卖车漏洞。

此前临时准备的“按格定位战车”实现仍保留了建筑条件，不能解决上述围墙场景，已经撤掉，未构建或发布。v1.0 的 EXE、DLL、标签与 Release 均未因此更换。尚未声称新增了可用的围墙卖车模式。

后续接入的验收必须包括：仅围墙且无建筑、实际收到的原版事件、单位被移除、原版现金增量，以及多人两端结果一致。成功排队和显示出售光标均不能单独作为完成证据。仍不允许功能私有 Hook、修改接收端、直接加钱或私改类型规则来拼出结果。

## 可重复执行的原版代码测试

测试脚本：`source/assist/tests/native_sell_refund_regression.py`。依赖 Python、pefile 和 Unicorn；游戏程序由使用者自行提供，不随源码分发。

```sh
python source/assist/tests/native_sell_refund_regression.py \
  /path/to/gamemd-spawn.exe /path/to/GameRuntime.dll \
  --output native-sell-audit.json
```

用户程序覆盖 112 项：12 项原版退款函数，96 项原版接收/出售/入账组合，以及 4 项围墙格子事件。四种会话分别覆盖原版单机/多人编号；这并非真实网络对局。

参考程序覆盖 64 项。它的 `Foot::Sell` 在 `0x4D9F79` 已被重定向到本模型未初始化的代码，48 项完整出售场景明确跳过，不还原、不绕过该补丁。仍可独立运行其原版退款函数、无建筑时的接收拒绝分支和围墙事件。跳过记录不能作为完整出售通过。

实际执行的原版代码包括用户程序的退款、接收判断和现金写入，以及两份程序可独立执行的退款与围墙分支。对象解析、声音、价格倍率、最终对象销毁及围墙重绘/寻路更新使用模型；测试验证销毁虚函数被调用，不能代替完整游戏中的对象生命周期验证。未加载 Ares/Phobos，也未运行 Windows 游戏或实际联机。

原始结果保存在仓库 `verification/sell-audit/`；每份结果绑定游戏程序与 v1.0 DLL 的 SHA-256。
